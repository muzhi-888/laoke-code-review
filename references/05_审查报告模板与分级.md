# 审查报告模板与严重度分级

审查意见写得好不好，直接决定作者改不改得动、改不改得对。本文件给分级标准和报告模板。

---

## 一、严重度分级

| 等级 | 含义 | 处理方式 |
|------|------|----------|
| CRITICAL | 安全/数据风险，上线即可能出事 | 必须改，一票否决 |
| HIGH | 正确性/稳定性硬伤，大概率出 bug | 必须改 |
| MEDIUM | 可维护性/性能隐患，长期会痛 | 建议改，需说明理由 |
| LOW | 风格/一致性小问题 | 可选，礼貌提示 |
| INFO | 疑问/建议/讨论点 | 不强制 |

**分级纪律**：
- 不要所有问题都标 HIGH——狼来了，作者会麻木。
- CRITICAL / HIGH 必须有"为什么危险"的具体解释，不能只说"不安全"。
- LOW 级的主观偏好（括号风格、变量名长短）标「建议」而非「必须改」。

---

## 二、单条意见的结构（黄金模板）

```
[严重度] 位置（文件:行）
问题：用一句话说清"哪里不对 / 会有什么后果"
建议：给具体改法（最好贴修正片段）
理由（可选）：为什么这样更好
```

反面教材（差）：
> 这里写得不好。（没说哪、为什么、怎么改）

正面教材（好）：
```
[HIGH] auth.py:42
问题：token 校验失败后只 return None，调用方误当"未登录"放行，存在越权。
建议：校验失败显式抛异常或返回 (False, reason)，调用方必须处理。
理由：静默失败是越权漏洞温床。
```

## 三、整体审查报告模板

审查完一个 PR / 一个模块，给作者一份总览：

```markdown
# 代码审查报告：<主题/PR>

## 总评
<一句话结论：可合并 / 需修改后合并 / 需讨论>

## 统计
- CRITICAL: n   HIGH: n   MEDIUM: n   LOW: n
- 核心问题：<最关键的一两条>

## 必须修改（CRITICAL/HIGH）
1. [文件:行] 问题 + 建议
2. ...

## 建议修改（MEDIUM）
- ...

## 讨论 / 疑问（INFO）
- 这里我不太确定需求，想确认：xxx

## 亮点
- <做得好的地方也写出来，不只是挑刺>
```

---

## 四、审查礼仪（很重要）

- **对事不对人**：说"这段代码在空输入时会崩"，不说"你又没判空"。
- **给方案不给命令**：「建议改成 X，因为 Y」比「你必须改」更易被执行。
- **区分阻塞与非阻塞**：能合并的小问题别卡着不让过；真会出事的才拦。
- **点赞好的实现**：看到优雅的处理，说出来。正向反馈让作者更愿意听你的意见。
- **不抢实现权**：除非明显错误，给方向让作者自己改，别替他写每一行。

## 五、和自动化扫描的配合

本 Skill 的 `review_scan.py` 负责"机械红线"——密钥、注入、裸 except、弱哈希、调试残留等。
它能把这类低级但致命的问题先捞出来，让你把精力放在：
- 业务逻辑对不对
- 设计合不合理
- 边界覆盖了没

**扫描器代替不了人审**，它只是把人从重复劳动里解放出来。报告里务必写明这一点，避免作者误以为"扫描过了就安全"。
