# 可维护性与可读性规则

代码写完只是开始，能改、敢改才是资产。下面是可维护 / 可读维度的具体规则，按"必须改"和"建议"分级。

---

## 一、命名（最便宜的改进）

**必须改**：
- 无意义的单字母 / 缩写：`a`、`tmp`、`data2`、`obj`、`h`（除非作用域极小如循环变量 `i`）。
- 误导性的命名：`user_list` 实际是 dict；`is_active` 实际可能是"已删除"。
- 中英文混用且无统一规范（一个项目里 `getUserName` 和 `取得用户` 并存）。

**建议**：
- 布尔变量加 `is_` / `has_` / `can_` 前缀（`is_valid`、`can_retry`）。
- 集合用复数（`users`、`orders`）；单条用单数（`user`、`order`）。
- 函数名用动词或动词短语（`fetch_orders`、`validate_input`）。

---

## 二、函数粒度

**必须改**：
- 单函数超过 ~60 行且做了多件事 → 拆分单一职责函数。
- 一个函数里既有 IO、又有业务判断、又有格式化输出 → 分层。

**建议**：
- 用"提前返回"替代深层嵌套：
```python
# ❌ 嵌套地狱
def process(x):
    if x:
        if x.valid:
            if x.active:
                do(x)
# ✅ guard clause
def process(x):
    if not x: return
    if not x.valid: return
    if not x.active: return
    do(x)
```

---

## 三、魔法数字与常量

**必须改**：
```python
if retries > 3: ...        # 3 是什么？
sleep(0.05)                # 50ms 为什么？
```
**正确做法**：提常量 `MAX_RETRIES = 3`、`RETRY_INTERVAL = 0.05`，名字即文档。

---

## 四、重复代码（DRY 但有度）

**建议**：
- 同样逻辑复制 3 处以上 → 抽公共函数。
- 但别为了 DRY 抽象出"只有一处用"的泛型函数——过度抽象比重复更费解。
- 抽象要看"变化的轴"：如果两处只是此刻恰好相同、未来会往不同方向演化，保留重复更稳。

---

## 五、注释

**必须改**：
- 大段被注释掉的死代码 → 删（版本管理能找回）。
- 纯复述代码的注释：`x = x + 1  # x 加 1` → 不如不写。

**建议**：
- 注释解释"为什么"而非"是什么"：
```python
# 为什么重试 3 次：上游网关偶发 503，重试可自愈（经验值）
```
- 非常规业务逻辑、踩过的坑、临时方案的欠条，一定要写注释。

---

## 六、复杂度

**必须改**：
- 圈复杂度过高（一个函数里 `if/for/except` 嵌套超过 4 层）→ 拆函数或用查表法（dict 映射）。
- 超长布尔表达式（一行十几个 `and/or`）→ 拆成命名良好的中间变量或独立判断函数。

---

## 七、依赖与接口

**建议**：
- 函数是否依赖了过多全局状态？能否改成显式传参（更易测）？
- 公共函数的入参/出参是否有清晰约定？改签名是否要同步改调用方？

---

## 经验法则

> 可读性没有"客观满分"，但有"客观不及格"：别人读这段代码需要反复猜意图，就是不及格。
> 维护成本 >> 写代码成本。第一次写清爽，省的是未来所有人反复返工的时间。
