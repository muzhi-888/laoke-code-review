# 性能与并发反模式

性能问题分两类：一类是 review 阶段就该拦的"明显会炸"（下面前几条），另一类是上线后压测才暴露的（不在 review 范围）。本文件只列前者。

---

## 一、N+1 查询（最高频）

**危险写法**：循环里查数据库。
```python
for user in users:
    orders = db.query("SELECT * FROM orders WHERE uid = ?", user.id)  # 每次循环一次查询
```
1000 个用户 = 1001 次查询。判 MEDIUM / HIGH（视数据量）。
**正确做法**：一次 `JOIN` 或 `IN (...)` 批量取，再在内存里分组。
```python
ids = [u.id for u in users]
orders = db.query("SELECT * FROM orders WHERE uid IN ?", (ids,))
```

---

## 二、循环内做网络 / IO

同步 `requests.get` 放在循环里、逐个调用第三方 API，延迟累加致命。
**正确做法**：批量化 / 并发（`asyncio.gather`、线程池）/ 或上游聚合接口。

---

## 三、全表加载再过滤

```python
all_rows = db.query("SELECT * FROM big_table")   # 几百万行
result = [r for r in all_rows if r.status == 'active']
```
**正确做法**：把过滤下推到数据库（`WHERE status = 'active'`），只取需要的列。

---

## 四、不必要的深拷贝 / 大对象驻留

`copy.deepcopy(huge_obj)` 在热路径上极慢。审查要点：是否真的需要深拷贝？能否用不可变结构 + 复用？

---

## 五、同步阻塞卡住事件循环

在 `async` 函数里调用阻塞的同步 IO（如 `time.sleep`、`requests.get`），会卡住整个事件循环。
**正确做法**：用 `await asyncio.sleep`、用 `aiohttp` 等非阻塞客户端；CPU 密集任务丢进线程池 `run_in_executor`。

---

## 六、锁竞争与死锁

审查要点：
- 多个锁是否总是按固定顺序获取（否则易死锁）？
- 锁的粒度是否过大（把整张大表锁住只为了改一行）？
- 是否在持锁期间做了网络请求（锁被长时间占用）？

---

## 七、内存泄漏苗头

- 全局缓存无上限、无过期 → 无限增长。
- 事件监听器 / 回调注册了没注销。
- 大对象被长生命周期容器（单例、模块级 list）引用，无法 GC。

---

## 八、无谓的重复计算

同一结果在循环里反复算、反复正则编译。审查要点：`re.compile` 提到循环外；可缓存的查表结果用 `functools.lru_cache`。

---

## 审查判断准则

- 数据是"小打小闹"（几十条、本地）还是"可能放大"（用户量 × 循环）？后者必须拦。
- 不确定会不会成为瓶颈时，标「建议 + 理由」，让作者知道风险，不必硬卡。
- 性能优化铁律：**先测再改**。review 阶段只拦"明显错误"，不拦"风格差异"。
