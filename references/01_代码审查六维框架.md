# 代码审查六维框架

代码审查不是"找茬"，是质量兜底。一个变更好不好，不能只看"能不能跑"，要从六个维度分别打分。本 Skill 的所有审查动作都挂在这六个维度上。

---

## 维度一：正确性（Correctness）

最优先。代码是否真的实现了需求？边界条件、异常路径、空值、并发、超时有没有处理？

审查清单：
- 是否覆盖了需求里提到的所有分支与场景？
- 输入为空 / 超长 / 非预期类型时会发生什么？
- 循环与递归的终止条件是否确定？会不会死循环 / 栈溢出？
- 浮点比较是否用了容差（不要用 `==` 比浮点）？
- 时区、编码、货币精度等易错点有无处理？

常见陷阱：
- 用 `==` 比较浮点数
- 整数溢出（语言如 Go/Java 有溢出风险，Python 不会但有性能问题）
- 把异常吞掉导致静默失败
- 只测了 happy path，没测错误路径

---

## 维度二：安全性（Security）

红线维度。一旦出问题，可能是数据泄露、被拖库、被勒索。

审查清单（关键项）：
- 任何外部输入（用户输入、HTTP 参数、文件内容、第三方回调）是否做了校验与转义？
- SQL 是否参数化？有无字符串拼接？
- 密码、令牌、密钥是否硬编码在源码或配置里？
- 反序列化是否使用了不可信来源（Python pickle / Java 原生序列化高危）？
- 权限校验是否在每个入口都做了（不只是前端隐藏按钮）？
- 是否使用了 `eval` / `exec` 执行外部构造的字符串？

> 安全维度的事几乎无法靠"运行时发现"，必须在 review 阶段卡死。本 Skill 内置的静态扫描器（scripts/review_scan.py）专门覆盖这一类红线。

---

## 维度三：可维护性（Maintainability）

三个月后你自己还看得懂吗？别人接手要多久？

审查清单：
- 函数是否单一职责？一个函数超过 ~60 行就要警惕。
- 命名是否表达意图？`data2`、`tmp`、`handle()` 这类命名要打回。
- 是否有"魔法数字"？该提成常量。
- 相似逻辑是否复制粘贴了三处以上？该抽公共函数。
- 模块依赖是否清晰？有没有循环依赖？

经验值：单函数超过 60 行、单文件超过 600 行，可维护性显著下降，应拆分。

---

## 维度四：可读性（Readability）

代码是写给人看的，顺带给机器执行。

审查清单：
- 复杂表达式是否拆成有意义的临时变量？
- 注释是否解释"为什么"而非"是什么"？`# 加 1` 这种注释不如不写。
- 是否有大段被注释掉的死代码？该删。
- 布尔表达式是否过于嵌套？考虑提前返回（guard clause）。

---

## 维度五：性能（Performance）

不是 prematurely optimize，是避免"明显会炸"的写法。

审查清单：
- 有没有在循环里做网络请求 / 数据库查询（N+1 问题）？
- 有没有加载全表再内存过滤？
- 大对象是否不必要地深拷贝？
- 有没有同步阻塞调用卡住事件循环 / 线程池？

> 性能问题通常要在"能跑"之后才优化，但 N+1、全表扫描这类是 review 就该拦的。

---

## 维度六：可测试性（Testability）

改完你敢不敢发？

审查清单：
- 核心逻辑是否和 IO / 网络解耦，便于单测？
- 有没有为这个变更补测试？至少覆盖主路径与边界。
- 测试是否依赖全局状态 / 真实外部服务（难复现）？

---

## 怎么用这六维

1. 先过**安全性**和**正确性**——这两维不通过，一票否决，其余不用看。
2. 再过**可维护性 / 可读性**——决定长期成本。
3. 最后看**性能 / 可测试性**——决定上限。
4. 给每条问题标严重度（见 references/05），写清"为什么"和"怎么改"，不要只说"这不行"。

> 铁律：审查是协作，不是审判。每条意见要么给出可执行的修改建议，要么说明风险让作者自己权衡。纯主观偏好（"我喜欢这样写"）标为「建议」而非「必须改」。
